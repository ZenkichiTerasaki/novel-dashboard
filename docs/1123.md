### 現在の認証・権限・プロジェクト共有の仕様

#### 1. 認証・セッション管理の現状
- **認証方式**: ステートレス JWT（NestJS `@nestjs/jwt` + `passport-jwt`）。サーバー側でのセッションテーブルや Redis 管理は未実装。
- **ユーザー登録 (`POST /users`)**: `name`, `email`, `password` を受け取り、`bcrypt`（saltRounds=10）でハッシュ化して `User` テーブルに保存。
- **ログイン (`POST /auth/login`)**: `email` / `password` を検証し、ペイロード `{ sub: user.id, email: user.email }`・有効期限 `7d` の JWT を `access_token` として返却。
- **フロント側のトークン保持 (`frontend/lib/api.ts`)**: `localStorage`（キー名: `novel_dashboard_token`）に JWT を保存し、APIリクエスト時に `Authorization: Bearer <token>` ヘッダーで送信。
- **ログアウト**: フロント側で `localStorage` から削除するのみ（サーバー側でのトークン即時失効の仕組みはなし）。

#### 2. DBスキーマとロール (`ProjectRole`)
- `ProjectMember` テーブルで `(userId, projectId)` ごとにロールを管理（複合ユニーク制約あり）。
- ロールは3種類：`OWNER` / `EDITOR` / `VIEWER`。
- プロジェクト新規作成時、作成者がトランザクション内で自動的に `OWNER` として登録される。
- プロジェクト一覧 (`GET /projects`) は、自分が `ProjectMember` に所属しているプロジェクトのみ返却される。

#### 3. メンバー招待機能の現状
- **バックエンド**: `POST /projects/:projectId/members` のみ実装済み。
  - `OWNER` のみ実行可能。
  - リクエストBody: `{ email: string, role: 'EDITOR' | 'VIEWER' }`。
  - 登録済みユーザーのメールアドレスを指定すると、承認ステップなしで即座に `ProjectMember` に追加される。
- **未実装のもの**: メンバー一覧取得API、ロール変更API、メンバー削除/退出API、招待リンク/招待承認フロー、フロントエンドのメンバー管理UI一式。

### レビュー・セキュリティ洗い出しと改善提案
1. **SQLインジェクション対策の現状**
   - 現状すべて Prisma の型安全なクエリ（パラメータバインド）のみを使用しており、`$queryRawUnsafe` 等の生SQLは未使用のため、SQLiリスクは低い。今後も生SQLを避ける方針を維持すれば問題ない。
2. **現状コードで確認できた優先度の高いセキュリティ・バグ修正点**
   - **[高] イベント並替えAPIの認証・認可漏れ**: `backend/src/event/event.controller.ts` の `PATCH /scenarios/:scenarioId/events/order` に `@UseGuards(JwtAuthGuard)` と `requireEditor` チェックを追加する必要がある。
   - **[高] アセットAPIの無認証・ファイル検証不足**: `frontend/app/api/projects/[projectId]/assets/route.ts` に認証・ロールチェックがない。また、アップロード時の拡張子/MIMEタイプ制限・ファイルサイズ上限がない（例: HTMLやスクリプトのアップロード防止が必要）。AWS移行時に S3＋NestJS管理へ統合すると一括で解決できる。
   - **[中] `POST /users` のレスポンスにハッシュ済みパスワードが含まれている**: `UserService.create` の戻り値で `password` を除外（`select` 指定）すべき。あわせてメール重複時の409エラーハンドリング、パスワード長/強度バリデーションも追加推奨。
   - **[中] フロントのJWTペイロード解析バグ**: バックエンドは `{ sub: user.id, email }` を発行しているが、`frontend/providers/AuthProvider.tsx` は `payload.userId` を参照している。`payload.sub` を読む（または `/auth/me` エンドポイントを作ってサーバーからユーザー情報を取得する）形に直すべき。
   - **[低] デバッグ用コードの残存**: `GET /auth`（認証なし・`console.log(req.user)` のみ）や `project.controller.ts` の `console.log` は削除推奨。
   - **[本番向け]**: `helmet` によるセキュリティヘッダー設定、`@nestjs/throttler` によるログイン/登録のレート制限、`CORS_ORIGIN` の厳格化。
3. **セッションID / トークンの持ち方の検討**
   - 現状の `localStorage` 保存は、万が一XSSが発生した場合にトークンを盗まれやすい欠点がある。
   - 共有・外部公開を見据えるなら **HttpOnly + Secure + SameSite=Lax Cookie** への移行が推奨。
   - **方式の選び方**:
     - **案A（HttpOnly Cookie + サーバー側セッションID / DB or Redis保存）**: 強制ログアウト・アカウント停止・ロール変更の即時反映が簡単で管理しやすい。プロジェクト共有アプリと相性が良い。
     - **案B（HttpOnly Cookie + 短命アクセストークンJWT + リフレッシュトークンDB管理）**: ステートレスの利点を活かしつつ安全性と失効管理を両立可能。実装量はやや増える。
   - 学習・保守コストとのバランスを考えると、まずは **案A（セッションID方式）** か **案B（CookieベースJWT＋短命化）** を選ぶのが王道。
4. **ロールの役割明確化＆ロール別ダッシュボードについて**
   - **ロール定義の見直しポイント**: 現状 `DELETE /events/:id` と `DELETE /scenarios/:id` が `OWNER` 専用になっている。共同編集を想定すると「イベントの追加・編集・削除・並替え＝`EDITOR` 以上」「シナリオ削除・プロジェクト削除・メンバー管理＝`OWNER` のみ」「閲覧・プレビュー再生・CSV書き出し＝`VIEWER` 以上」のように線引きを明文化すると運用しやすい。
   - **ロール別ダッシュボード案**: 非常に良い方針。まず `GET /projects` / `GET /projects/:id` のレスポンスに `myRole`（または `members` の自分のロール）を返すようにすれば、フロント側で以下のように綺麗に切り分けられる。
     - `OWNER`: 全機能 ＋ メンバー管理タブ ＋ プロジェクト設定/削除
     - `EDITOR`: シナリオ・イベント編集 ＋ アセット管理 ＋ プレビュー（危険操作・メンバー管理は非表示）
     - `VIEWER`: 閲覧・ゲームプレビュー再生・CSV出力専用のクリーンなUI（フォームやドラッグ並替えを非表示）

### フォルダ構成・AWS移行に向けた改善案

1. **【最重要】アセット保存先をローカルFSから Amazon S3 (+ CloudFront) へ分離**
   - 現状は `frontend/public/assets/projects/{projectId}/` に画像や `presets.json` を直接書き込んでいる。
   - AWS（ECS / App Runner / Amplify 等）ではコンテナのローカルファイルは再デプロイで消失し、複数台構成でも共有できないため、**画像は S3 に保存**し、**プリセット設定は DB (`Project.presets`) に一本化**（`presets.json` の二重管理を廃止）するのが必須。
2. **アセットAPIの責務を `backend/` へ集約**
   - 現在 `frontend/app/api/projects/[projectId]/assets/route.ts` だけ Next.js 側にAPIが存在し、NestJS の認証・ロール制御と分断されている。
   - `backend/src/asset/` モジュールを新設し、「権限チェック → S3 署名付きURL（Presigned URL）発行 → フロントからS3へ直接アップロード」という構成にすると、セキュリティ・拡張性・帯域コストのすべてが改善する。
3. **フロントエンドのコンテナ化と環境変数整備**
   - `backend/Dockerfile` はあるが、`frontend/Dockerfile` と `frontend/.env.example` が未作成。
   - Next.js を `output: 'standalone'` でビルドする `frontend/Dockerfile` を追加し、`docker-compose.yml` に `frontend` サービスも定義しておくと、ローカル環境とAWS（ECS/App Runner等）の差異を減らせる。
   - また、`backend/Dockerfile` の起動コマンドで `npx prisma generate` や本番時の `npx prisma migrate deploy` の運用ルールを決めておくと事故を防げる。
4. **Prisma マイグレーション履歴の整備**
   - 現在 `schema.prisma` の `Project.presets` と `Event.data` 変更は `db push` で反映されており、`backend/prisma/migrations/` に対応するマイグレーションファイルが存在しない。
   - 本番DB（Amazon RDS）へ安全にデプロイするため、AWS移行前にマイグレーション履歴を整え、`prisma migrate deploy` で再現可能な状態にしておく必要がある。
5. **`infra/` ディレクトリの活用（IaC導入）**
   - 現在空になっている `infra/` 配下に、AWS構成図や **AWS CDK**（TypeScriptで書けるため本プロジェクトと相性が良い）または **Terraform** の定義ファイルを置くと、インフラ構成をコードで管理・学習できる。
6. **リポジトリ内の軽微な整理ポイント**
   - `docs/` 内に `System Specification.md` と `system-specification.md` が併存している（Windowsでは気付きにくいがLinux/Git上で競合・混乱のもとになるため統合推奨）。
   - `frontend/public/assets/projects/` 内のユーザーアップロード素材（日本語ファイル名含む）は `.gitignore` 対象とし、サンプル素材のみ別管理にするとリポジトリの肥大化や環境依存トラブルを防げる。
   - `frontend/types/project.ts` と `frontend/types/index.ts` の役割分担も整理しておくと見通しが良くなる。

### AWS構成の学習・移行ロードマップ案（おすすめ順）
1. **基本概念の把握**: IAM（最小権限）、VPC（パブリック/プライベートサブネット）、セキュリティグループ。
2. **マネージドサービス中心の最小構成で設計**:

   - **画像/音声素材**: Amazon S3 + CloudFront
